# 多観点レビュー

## この skill の目的

実装完了後・PR 前のブランチ差分に、複数の専門家観点の subagent を**並行**で
レビューさせ、発見を統合してユーザーの裁定用一覧を作る。狙いは2つ:

1. **挙動を変えないリファクタ候補**の網羅的な洗い出し
2. その過程で見つかる**挙動が変わる問題**（バグ・仕様との食い違い・運用リスク）の
   別枠報告 — 実績上、ここから最も価値の高い発見が出る

この skill の担当は**レビューと裁定用一覧まで**。コードの修正は一切しない。
裁定後の実装は通常フロー（コミット単位の計画 → 着手前ゲート → 証拠つき報告）に
接続する。

## 全体の流れ

1. 差分の把握
2. 観点の推薦（3〜5個）→ ユーザー確認
3. 観点の具体化（マニフェスト検出・ドメイン資料の質問）
4. 全観点を1メッセージで並行起動
5. 統合 → 裁定用一覧の提示 → 裁定待ち

### Step 1: 差分の把握

- base ブランチを確認し、`git diff <base>...HEAD --stat` で変更ファイル一覧と規模を見る
- 変更の種類（新機能・リファクタ・バグ修正）、規模、触っている層（API・DB・
  非同期ジョブ・外部連携・UI 等）を把握する。これが次の観点推薦の材料になる

### Step 2: 観点の推薦とユーザー確認

- [references/perspectives.md](references/perspectives.md) を読む。10観点のカタログで、
  各観点に「役割宣言・いつ有効か・チェックリスト」が定義されている
- 差分の内容から **3〜5観点**を選び、それぞれ「なぜこの差分に有効か」を1行で添える
- **毎回全部は走らせない**。コストを必ず明示する:
  1観点 約10万トークン・4〜5分（例: 4観点並行で計 約40万トークン）
- AskUserQuestion（multiSelect）で観点の追加・削除を確認してから起動する

### Step 3: 起動前の準備

- **言語・ライブラリの検出**: マニフェスト（pyproject.toml / go.mod / package.json /
  Gemfile / Cargo.toml 等）から言語バージョンと主要ライブラリを検出し、
  「言語プロ」「ライブラリプロ」観点のチェックリストを具体化する
- **ドメインエキスパート観点だけは自動化できない**。この観点を使うときは起動前に
  ユーザーに2点聞く:
  1. subagent に読ませる仕様資料はどれか（パスを具体的に）
  2. 蒸し返し禁止の「確定済み設計判断」はどこに書いてあるか
- **確定済み判断の資料は、選ばれた全観点のプロンプトに渡す**。渡さないと subagent が
  既決事項を蒸し返す発見を量産する（実績: 設計資料を渡したことでほぼゼロだった）

### Step 4: 並行起動

- 全観点の Agent tool 呼び出しを**1つのメッセージにまとめて同時に**投げる。
  subagent はバックグラウンド実行なので、直列に待つのは時間の無駄
- subagent_type は general-purpose、モデルは**利用可能な最強のもの**を指定する
  （この skill 作成時点では fable）
- 各観点のプロンプトは後述の骨格に従う。**全観点共通の制約**（挙動不変・別枠報告・
  蒸し返し禁止・読み取り専用）を全プロンプトに埋めることが品質の核

### Step 5: 統合と裁定用一覧

統合の手順:

1. **重複排除**。複数観点が独立に同じ箇所を指摘したら、それ自体が強いシグナル。
   「N観点が独立に指摘」と明記する（裁定の優先度付けに効く。
   実績: 4観点中3観点が同一箇所の二重管理を独立指摘 → 最初に着手する判断材料になった）
2. **「⚠️挙動が変わる・要判断」と「挙動不変のリファクタ」を分けて提示**する。
   前者を先頭に置く
3. 挙動不変側は「構造」「可読性・ドメイン語彙」「テスト」等に分類し、
   **重要度×工数の表**にまとめる
4. 最後に「**議論したい点**」を2〜3個に絞って提示し、ユーザーの裁定を待つ。
   **勝手に直さない**

一覧の言葉づかい:

- 発見 ID は観点別の接頭辞（P-1, L-2 など。カタログに定義）で内部管理してよい。
  出所が追えて統合後に便利
- ただしユーザーに見せる一覧では意味の読めない略号・造語を作らない。
  タイトルは内容がそのまま読める平易な日本語にする

### Step 6: 出口

裁定で「やる」と決まった項目をコミット単位のタスクに分解し、通常の実装フロー
（着手前ゲート → 証拠つき報告）へ接続する。この skill の担当はここまで。

## subagent プロンプトの骨格

各観点のプロンプトは以下の骨格の変奏。`{}` を起動時に埋める。
チェックリストは perspectives.md の該当観点から取り、Step 3 の検出結果で具体化する。

```
あなたは {観点の役割宣言} として、リポジトリ {path} のブランチ {branch} の
新規コードをレビューする。読み取り専用のレビューであり、ファイルの変更は一切禁止。

## 対象
`git diff {base}...HEAD --stat` で変更ファイル一覧が見られる。主対象: {ファイル群の列挙}
背景資料: {設計資料のパス}（確定済みの設計判断が書かれている。設計判断そのものは蒸し返さない）

## レビューの前提
- 目的は「仕様・挙動を一切変えないリファクタリング」の候補を洗い出すこと。
  挙動が変わる提案は不可。ただし挙動バグ・仕様との食い違い・運用リスクを見つけたら
  「リファクタではなくバグ/リスク」と明示して別枠で報告する（この別枠報告は歓迎される）
- 確定済みの設計判断（{要点の列挙}）は前提として受け入れる

## 観点（{観点名}として）
{観点のチェックリスト 5〜8項目}

## 出力形式（最終メッセージ。日本語）
発見ごとに:
- **[{接頭辞}-連番] タイトル**（file_path:line）
- 重要度: 高/中/低、工数: 小/中/大
- 現状の何が問題か（1〜3行、具体例つき）
- 改善案（具体的に。before/after のコード断片が有効なら短く示す）
- 挙動不変であることの根拠（1行）

重要度順に並べる。最大{N}件。確信度の低いものは「確信度低」と明示する。
{観点固有の追加指示（例: 既存コードベースの慣習とのズレは必ず指摘）}
```

書式を全観点で統一するのは、統合（Step 5）を機械的にやるため。
最大件数 `{N}` は 12〜15 を目安にする。
