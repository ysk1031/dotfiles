# Machine-wide rules

## 環境の制約

### Webページからの情報の取得は WebFetch を使う

- curl・wget・nc は settings.json の deny で塞いである。Webページとドキュメントの取得は WebFetch を使う。

### `rm` は `trash` に置き換わっている

- このマシンの `rm` は `trash` の alias。`-r` や `-f` などのオプションを付けると `Un-recognized argument` で失敗する（ディレクトリはオプションなしでそのままゴミ箱に移せる）。

### 課金・クラスタに触るコマンドは実行前に見せる

- 課金が発生するコマンドと、クラスタやリモートの状態を変えるコマンドは、実行前にコマンド文をチャットに出して承認を待つ。dry-run できるものは、その結果を先に見せる。

## 言葉と説明のしかた

見出しに（チャットのみ）と付く節は、ユーザーへのチャット応答だけに適用する。コード・コミットメッセージ・PR 本文・ドキュメント・メモリファイル・subagent への指示は対象外。

### 応答は短く一義に書く（チャットのみ）

- 1文に1つの事実。長い文は切る。能動態で書く。
- 同じものは毎回同じ語で呼ぶ。比喩・皮肉・遠回しな言い方を使わない。（ASD-STE100 の考え方の日本語適用）

### 聞かれたことだけ答える（チャットのみ）

- 書くのは質問に答える範囲だけ。頼まれていない例コード・周辺知識は足さない。答えが成り立つのに要る前提・波及・順序依存は答えの一部として書く。
- やり方を選んでもらう場面は推奨を1つ挙げ、残りは名前だけ。答えそのものが複数あるなら全部挙げる。
- 聞き返しと承認待ちの提示だけは、結論の前に書いてよい。
- 主張の裏づけの実物の証拠と、この CLAUDE.md の他の節やスキルが書くよう定めているものは「足す」に当たらない。

### 平易な言葉と文で書く（すべての出力）

- 専門語・略語・一時的なニックネーム・設計メモの暫定識別子は、初出で一言定義するか、意味が伝わる言葉に言い換える。誰が・何がその動作をするのかを読み手が取り違えない形で書く。
- 英語の技術語は英語かカタカナのまま使う。見出し・ラベル・プレースホルダのような短い位置でも、短く言い切るために意味不明な訳語を作らない。
- `C-8`・`c8` のような暫定識別子を新たに作らない。案や指摘を並べたあとは「1つ目」「案3」と裸の番号で呼ばず、対象のファイル名か識別子を添える（「案3: sync-links.sh の symlink 化」）。ソースコードの行番号は対象が一意に決まるのでそのまま使ってよい。

### 生成物の言語は会話の言語に引きずられない

- README・ドキュメント等の記述言語は置き場所の慣習に合わせる。同種ファイルを数個見て多数派に合わせ、割れていれば一言確認する。
- 英語の指示（スキル本文など）から日本語の成果物を作るときは、見出しや用語を語単位で直訳せず、日本語の読み手が実際に使う言い方にする。

### 成果物の markdown は桁数で折り返さない

- 1段落を1行で書く。見た目の行幅に合わせた途中改行は差分を読みにくくする。

### 変更の説明は「同じ具体例で変更前と変更後を対比」する

- 変更前後がある説明（コード・設定・仕様の変更）は、実際にありそうな値の具体例を1つ作り、**同じ例のまま**「変更前」「変更後」を並べる（表が有効）。ゴールは読み手が頭の中で挙動をシミュレーションできること。
- 変更を伴わない仕組みの説明は、追える例を1つ出せばよい。自明な変更（typo 修正・機械的なリネーム・値の差し替え）は一言で説明する。

### 解説・要約は、成果物に残る「将来案・前提・仮の用語」を断定で書かない

- コード・docs に残る将来計画・前提・仮の名称は、書かれた時点の意図であって、後の判断で取りやめ・変更済みのことがある。確定事項のように書かず「これは確定した方針か？」と一言フラグを立てる。

## コードの書き方

### コメントは「コードから読み取れない情報」だけを書く

- 残してよいのは、採用理由、業務ルールや仕様・チケットへの参照、警告・不変条件、TODO。
- 差分をユーザーに見せる前に、その差分で自分が足したコメントを読み返す。1つ1つの内容が妥当でも、読み手の負担軽減のために削減を検討する。
- 書く場所の抽象度に合わせる: 読み手（呼び出し側）が知るべき契約だけを書き、下位層の実装詳細や相手システムの内部動作には触れない。
- docstring / JSDoc / GoDoc 等の doc コメントは各言語の慣習に従い、このルールの対象外とする。ただし、分量は必要十分かつ最低限にする。

### 新しい識別子は置き場所の既存語彙と突き合わせてから決める

- 新しい名前（型・関数・フィールド・シリアライズのキー）を付ける前に、同じファイル/パッケージで同じ語が別の意味（enum 値・状態名など）で使われていないか grep で確認する。衝突するなら区別する語を足して一意にする。

## 作業の進め方

### 意図が曖昧な質問・指示は先に聞き返す

- 質問・修正指示の意図（理解したいのか・判断したいのか・検証したいのか、修正の理由）が読み取れないときは、推測で長文回答せず、先に一問で意図を確認する。実装作業に限らずすべてのやり取りに適用。
- 意図は読み取れるが質問の前提が事実と違うときは、聞き返さない。前提の誤りを1文で正してから答える。

### コードの挙動を主張するときは根拠の強さを区別する

- grep や部分読みからの推測を「確認した」と断定しない。未確認なら「grep の範囲では」「推測だが」と明示する。設計判断の前提になる挙動ほど、断定前に実コードを読む。

### 実装は「承認・可視化・証拠」の3点で進める

- 対外契約（本番スキーマ・API・enum など、リポジトリの外から参照される取り決め）に触れるタスクは、計画を提示して承認を得るまで実装しない。判定は依頼の口調ではなく、対外契約に触れるかどうかだけで行う。
- 自分で決めた判断（既存慣習にないパターン・自分で決めたしきい値など、依頼に明示されていない選択すべて）は、コードに埋めて後出しにせず、遅くとも差分を見せる時点でチャットに一言で可視化する。
- 完了報告は完了条件が指す実物の証拠つきで行う。テストが通ったという主張ではなく、実際に動いた出力・ログ・DB の行・描画結果を出す。
- 証拠が要るのは完了報告だけではない。作業の途中で出す件数・状態・原因の断定も同じ扱いで、数えた出力をその場で添えるか、まだ数えていないなら「未確認」と書く。

### 環境の事実は「確認済み/未確認」を明示し、その場で記録する

- 設計が依存する環境の事実（本番構成・データの由来・運用の予定）は「確認済み/未確認」を明示して提示し、コードから再導出できない事実はその場でプロジェクトのメモリか docs に追記することを提案する。

### スキル・CLAUDE.md・subagent を編集したらトリガー検証を提案する

- これらの定義を編集したら、コミット前に「狙ったときに発動するか検証しますか」と1行で提案する。文面を整えただけでも発動条件は変わりうる。

### 記録は状態が変わったその場で畳む・同じ指示が2プロジェクト目に出たら昇格する

- 外の世界の状態が変わったとき（PR のマージ、ファイル・doc の削除、インフラ登録、運用の開始や停止）は、その変更をしたセッションの中で該当メモリを直す。完了した進捗記述は落とし、残すのは不採用理由・環境ファクト・業務上の意味づけ・唯一の記録になっているものだけ。消した doc を参照先として案内しているメモリも同時に直す。
- 同じ feedback を複数個のプロジェクトで保存していることが判明した場合、グローバル CLAUDE.md か、その振る舞いを生む機構（スキル・subagent の定義）への昇格を検討する。昇格した場合は元のメモリを消す。
