# Develop Skill

Orchestrator skill that runs the research → plan → implement pipeline end-to-end. Reuses existing `prompts/*.md` from the three individual skills to coordinate investigation, planning, and implementation automatically.

## Instructions

### Argument Parsing (Main Entry Point)

**Arguments**: $ARGUMENTS

Extract the following variables:

| Variable | Description | Default |
|----------|-------------|---------|
| `TASK` | Task description (all text except `--from`, `--research`, `--output` flags) | — |
| `FROM` | Starting phase (`--from` flag value) | `research` |
| `RESEARCH_FILE` | Existing research file path (`--research` flag value) | — |
| `OUTPUT` | Plan output filename (`--output` flag value) | `plan.md` |

**Phase Branching**:

- `--from research` (default): Phase R → Phase P → Phase I
- `--from plan`: Phase P → Phase I
- `--from implement`: Phase I only

**Validation**:

1. If `FROM` is `research` or `plan` and `TASK` is empty:
   ```
   タスクの説明を指定してください。例: /develop "ユーザー認証機能の追加"
   ```
   Display message and stop.

2. If `FROM` is `implement` and the plan file is not found:
   Use `OUTPUT` value (default: `plan.md`) as the plan file path.
   ```bash
   if [ ! -f "$PLAN_FILE" ]; then
     ls plan*.md 2>/dev/null | head -5
   fi
   ```
   If not found:
   ```
   計画ファイルが見つかりません。先に /plan でファイルを作成するか、--output でパスを指定してください。
   利用可能なファイル: <list or なし>
   ```
   Display message and stop.

After validation passes, execute phases sequentially starting from the `FROM` value.

---

### Phase R: Research (executed when `FROM` is `research`)

Phase R performs the same processing as the existing `/research` skill, but skips the review gate and outputs automatically.

#### Phase R-1: Scope Determination (Task + subagent)

Call the Task tool with:
- subagent_type: "general-purpose"
- description: "determine research scope"
- prompt: Read the file `~/.claude/skills/research/prompts/analyze-scope.md` and use its content as the subagent prompt. Replace `$ARGUMENTS` with the TASK value. Apply the following overrides:
  - **SCOPE**: Always set to `"broad"` — ignore `--scope` flag parsing
  - **OUTPUT**: Always set to empty — Phase R determines this automatically
  - **NO_TOPIC error message**: Use `/develop "認証フロー"` as the example (not `/research`)

---

**Phase R-1 Error Handling**:

- `NO_TOPIC`: Display error message and stop (should be caught by argument parsing, but acts as fallback)
- `ENTRY_POINT_COUNT: 0`: Use AskUserQuestion:
  - question: "`<topic>` に関連するファイルが見つかりませんでした。キーワードやパスを変えて再試行しますか？"
  - header: "Research"
  - options:
    1. label: "キーワードを変更", description: "別のキーワードで検索します（Otherで入力）"
    2. label: "キャンセル", description: "調査を終了します"
  - "キーワードを変更": Re-run Phase R-1 with the new keyword
  - "キャンセル": Display "調査を終了しました。" and stop

#### Phase R-2: Deep Investigation (Task + general-purpose subagent)

Call the Task tool with:
- subagent_type: "general-purpose"
- description: "deep codebase investigation"
- prompt: Read `~/.claude/skills/research/prompts/investigate.md` with the Read tool and use its content as the subagent prompt. Embed the Phase R-1 output as `Scope Data` and TASK as `Investigation Topic`. Set `Previous Findings` and `Follow-up Request` to empty.

#### Phase R-3: Automatic Output (no review gate)

After receiving Phase R-2 results, automatically output the research file without a review gate.

1. **Determine filename**: `research-<sanitized-topic>.md`
   - Sanitize: lowercase, replace spaces/special chars with hyphens, collapse consecutive hyphens
2. **Write file**: Use the Write tool to output the research document with the following structure:

```markdown
# Research: <topic>

> Generated by Claude Code develop skill on <date>
> Scope: broad

## 概要

<2-3 sentence overview>

## アーキテクチャ

<Architecture description>

## 主要コンポーネント

### <Component 1>
- **ファイル**: `<path>`
- **責務**: <what it does>
- **依存先**: <what it depends on>
- **依存元**: <what depends on it>

## データフロー

<Data flow description>

## 既存パターンと規約

<Patterns and conventions>

## 依存関係

<Dependencies>

## 注意点・リスク

<Risks and gotchas>

## 関連ファイル一覧

<File list grouped by role>
```

3. **Display summary**:

```
## Phase R 完了: 調査結果

**トピック**: <topic>
**出力ファイル**: <filename>
**調査ファイル数**: <count>

### 主要な発見
<key findings — 3-5 bullet points>

Phase P（計画生成）に自動遷移します...
```

4. Set `RESEARCH_FILE` to the output file path and transition to Phase P.

---

### Phase P: Plan (executed when `FROM` is `research` or `plan`)

Phase P performs the same processing as the existing `/plan` skill. It maintains the annotation cycle (the only confirmation gate) and automatically transitions to Phase I after approval.

#### Phase P-1: Context Gathering (Task + subagent)

RESEARCH_FILE resolution:
- If Phase R was executed: use the file path output in Phase R-3
- If `--from plan`: use the `--research` flag value
- If `--from plan` without `--research`: search for `research-*.md` in the current directory and display candidates (do NOT auto-select)

Call the Task tool with:
- subagent_type: "general-purpose"
- description: "gather planning context"
- prompt: Read the file `~/.claude/skills/plan/prompts/gather-context.md` and use its content as the subagent prompt. Replace `$ARGUMENTS` with the TASK value. Apply the following overrides:
  - **TASK**: Already validated as non-empty — skip the NO_TASK validation in Step 1
  - **RESEARCH_FILE**: Use the resolved RESEARCH_FILE value from above
  - **OUTPUT**: Use the `$OUTPUT` value (default: `plan.md`)

---

**Phase P-1 Error Handling (when `--from plan`)**:

- `RESEARCH: NOT_FOUND` (specified research file not found):
  Use AskUserQuestion:
  - question: "指定された調査ファイル `<path>` が見つかりません。どうしますか？"
  - header: "Research File"
  - options:
    1. label: "なしで続行", description: "調査ファイルなしで計画を生成します"
    2. label: "パスを変更", description: "別のファイルを指定します（Otherで入力）"
    3. label: "キャンセル", description: "パイプラインを終了します"
  - "なしで続行": Clear RESEARCH_FILE and proceed to Phase P-2
  - "パスを変更": Re-run Phase P-1 Step 2 with new path
  - "キャンセル": Display "開発を終了しました。" and stop

#### Phase P-2: Plan Generation (Task + general-purpose subagent)

Call the Task tool with:
- subagent_type: "general-purpose"
- description: "generate implementation plan"
- prompt: Read `~/.claude/skills/plan/prompts/generate-plan.md` with the Read tool and use its content as the subagent prompt. Embed the Phase P-1 output as `Context Data` and TASK as `Task Description`. If RESEARCH_FILE exists, instruct the subagent to read it with the Read tool.

#### Phase P-3: Annotation Cycle (repeat until approved — the ONLY confirmation gate)

**Step 1: Write Plan File**

Filename: `OUTPUT` value (default: `plan.md`)

Write the plan using the Write tool with this structure:

```markdown
# Plan: <task description>

> Generated by Claude Code develop skill on <date>

## 背景

<Why this task is needed>

## ゴール

<Specific, measurable outcomes>

## 実装ステップ

### 1. <step title>
- **対象ファイル**: `<path>` (create / modify)
- **変更内容**: <specific changes>
- **理由**: <why>
- **詳細**:
  <detailed description>

### 2. <step title>
...

## テスト計画

<How to verify>

## リスクと考慮事項

<Risks>

## チェックリスト

- [ ] Step 1: <brief>
- [ ] Step 2: <brief>
...
```

**Step 2: Open in Editor**

```bash
code <filename> 2>/dev/null || true
```

**Step 3: User Review**

Display the plan summary:

```
## 計画レビュー

計画を `<filename>` に出力しました。エディタで開いています。

計画の概要:
- **全<N>ステップ** で <概要>
<各ステップの簡潔なサマリーリスト>

計画を確認してください。エディタでインライン注釈を書き込んでから「注釈を反映」を選択すると、注釈を反映した計画を再生成します。問題なければ「承認」とお知らせください。キャンセルする場合は「キャンセル」とお知らせください。
```

Use AskUserQuestion:
- question: "計画を確認してください。エディタでインライン注釈を書き込んでから「注釈を反映」を選択すると、注釈を反映した計画を再生成します。"
- header: "Plan Review"
- options:
  1. label: "承認", description: "この計画で実装に進めます"
  2. label: "注釈を反映", description: "ファイルに書き込んだ注釈を反映して再生成します"
  3. label: "キャンセル", description: "パイプラインを終了します"

**If "承認"**: Proceed to Phase P-4.

**If "注釈を反映"**:
1. Read the plan file with the Read tool
2. Regenerate the plan with the Task tool:
   - subagent_type: "general-purpose"
   - description: "revise plan with annotations"
   - prompt: Read `~/.claude/skills/plan/prompts/revise-plan.md` with the Read tool and use its content as the subagent prompt. Embed the annotated plan file content as `Annotated Plan` and the Phase P-1 context as `Context Data`.
3. Overwrite the plan file with the Write tool
4. Loop back to Step 2 (open in editor + ask for review again)

**If custom input (Other)**: Treat the user's input as verbal annotation. Regenerate using the same flow as "注釈を反映" but include the user's text as additional context.

**If "キャンセル"**: Display "開発を終了しました。" and stop.

#### Phase P-4: Finalization

1. Read the approved plan file with the Read tool
2. Verify the checklist section matches all implementation steps
3. Update the plan file if the checklist needed corrections

Display:
```
## Phase P 完了: 計画確定

`<filename>` が承認されました。

### チェックリスト
<display checklist>

Phase I（実装）に自動遷移します...
```

4. Automatically transition to Phase I.

### Phase I: Implement (executed in all flows)

Phase I performs the same processing as the existing `/implement` skill, but skips scope confirmation (AskUserQuestion) and auto-executes all steps.

#### Phase I-1: Plan Loading & Tooling Detection (Task + subagent)

Plan file path resolution:
- If Phase P was executed: use `OUTPUT` value (default: `plan.md`)
- If `--from implement`: use `OUTPUT` value (default: `plan.md`)

Call the Task tool with:
- subagent_type: "general-purpose"
- description: "load plan and detect tooling"
- prompt: Read the file `~/.claude/skills/implement/prompts/load-plan.md` and use its content as the subagent prompt. Replace `$ARGUMENTS` with the resolved plan file path. Apply the following overrides:
  - **Step 1 (Parse Arguments)**: Skip entirely — `PLAN_FILE` is the resolved plan file path from above, `STEPS` is always ALL
  - **SELECTED_STEPS**: Omit from the return result — `/develop` always executes all steps
  - **NO_PLAN error message**: Use shorter version: `計画ファイルが見つかりません。`

---

#### Phase I-2: Implementation Loop (skip scope confirmation → auto-execute all steps)

**Skip the existing `/implement` Phase 2 (scope confirmation AskUserQuestion) and immediately auto-execute all remaining steps.**

If CLAUDE.md exists, read it with the Read tool to follow project conventions.

Execute each remaining step in order:

##### Step I-2.1: Read Step Details

Re-read the plan file with the Read tool to get the current step's details:
- Target file and action (create / modify)
- Specific changes to make
- Reasoning and details

##### Step I-2.2: Implement

Based on the step action:

**modify**:
1. Read the target file with the Read tool
2. Apply changes using the Edit tool
3. If the edit is too large or complex, use Write to rewrite the file

**create**:
1. Verify the parent directory exists: `ls <parent-dir>`
2. Write the new file with the Write tool

**delete** (if specified):
1. Confirm with the user before deleting
2. Use Bash `rm` to delete

Implementation guidelines:
- Follow patterns specified in the plan
- Do NOT add comments, JSDoc, or type annotations not in the plan
- Do NOT add features, error handling, or abstractions not in the plan
- Keep changes minimal and focused

##### Step I-2.3: Validate

After each step, run detected validation commands:

1. **Type check** (if available): Run via Bash
2. **Lint** (if available): Run via Bash

If validation fails:
- Read the error output
- Fix the issue immediately
- Re-run validation to confirm the fix
- Do NOT move to the next step until validation passes

If validation passes, continue to the next step without pausing.

**IMPORTANT**: Do NOT run the full test suite after every step — only run type check and lint. Tests are run once in Phase I-3.

##### Step I-2.4: Update Checklist

After each step completes successfully (including validation):
1. Read the plan file with the Read tool
2. Update the checklist: change `- [ ] Step N: ...` to `- [x] Step N: ...`
3. Update the plan file using the Edit tool

Then immediately proceed to the next step. Do NOT ask for user confirmation between steps.

---

#### Phase I-3: Verification & Summary

After all steps are complete:

1. **Run full test suite** (if available):

If tests fail:
- Display the failure output
- Use AskUserQuestion:
  - question: "テストが失敗しました。修正を試みますか？"
  - header: "Test Failure"
  - options:
    1. label: "修正する", description: "失敗したテストを分析して修正します"
    2. label: "スキップ", description: "テスト失敗を無視して完了とします"
  - "修正する": Analyze the test failure, fix the issue, re-run tests. Repeat until tests pass or user chooses to skip.
  - "スキップ": Proceed to summary.

2. **Show summary**:

```bash
git diff --stat
```

3. **Display completion message**:

```
## 実装完了

### 変更されたファイル
<git diff --stat output>

### チェックリスト
<updated checklist — all implemented steps should be checked>

### 検証結果
- Type check: <PASS / FAIL / N/A>
- Lint: <PASS / FAIL / N/A>
- Test: <PASS / FAIL / SKIPPED / N/A>

### 次のステップ
- 動作確認を行ってください
- 問題なければ `/commit` でコミットできます
```

### Error Handling and `--from` Mid-Pipeline Start

#### Precondition Validation for Mid-Pipeline Start

Validate preconditions at each phase start. In addition to the argument parsing validation, the following checks are performed within each phase:

##### When `--from plan`

Start from Phase P. Validate:

1. **TASK is required**: Already stopped in argument parsing if empty (fallback)
2. **If `--research` is specified**: Check file existence
   - Not found: Phase P-1 error handling via AskUserQuestion ("なしで続行" / "パスを変更" / "キャンセル")
3. **If `--research` is not specified**: Search for `research-*.md` and display candidates (do NOT auto-select — informational only)

##### When `--from implement`

Start from Phase I. Validate:

1. **TASK is not required**: Read from the plan file
2. **Plan file existence check**: `OUTPUT` value (default: `plan.md`)
   - Not found: Search for `plan*.md` and display candidates
   - No candidates either:
     ```
     計画ファイルが見つかりません。先に /plan または /develop でファイルを作成するか、--output でパスを指定してください。
     利用可能なファイル: なし
     ```
     Display message and stop.

#### Error Handling Summary

| Situation | Phase | Response |
|-----------|-------|----------|
| Task description empty | Argument parsing | Display error message and stop |
| Topic not specified in Phase R | Phase R-1 | Display error message and stop (fallback) |
| 0 entry points in Phase R | Phase R-1 | AskUserQuestion: change keyword or cancel |
| Research file not found with `--from plan` | Phase P-1 | AskUserQuestion: continue without / change path / cancel |
| Cancel during annotation cycle | Phase P-3 | Terminate entire pipeline |
| Plan file not found with `--from implement` | Argument parsing | Display error message + candidates and stop |
| Validation failure in Phase I | Phase I-2.3 | Fix immediately → re-validate |
| Test failure in Phase I | Phase I-3 | AskUserQuestion: fix or skip |

### Rules

- ALWAYS display messages in Japanese — ユーザーが日本語話者であり、パイプライン全体の進捗を日本語で確認する必要があるため
- NEVER modify existing skills — `/develop` is an independent new skill — 既存スキルを変更すると、個別スキル（`/research` 等）の単独利用に影響が出る
- NEVER skip the plan annotation cycle (Phase P-3) — 計画の承認がパイプライン唯一の確認ゲートであり、これを飛ばすと意図しない変更が実装される
- Skip the review gate in Research phase — auto-output in Phase R-3 — パイプライン内では調査は中間成果物であり、計画レビューで最終確認できるため
- Skip scope confirmation in Implement phase — auto-execute all steps in Phase I-2 — 計画承認済みのため、実装開始の再確認は冗長
- Reference existing `prompts/*.md` directly to minimize logic duplication — プロンプト変更が自動的に反映され、メンテナンスコストが下がる
- When starting mid-pipeline with `--from`, validate preconditions for skipped phases — 前提条件が満たされない状態で後続フェーズを実行するとエラーや不完全な結果になる
- NEVER commit or push changes — Phase I only applies file modifications — コミットはユーザーが変更を確認した後に行うべき
- NEVER add comments, JSDoc, or type annotations not specified in the plan — 計画にない追加はスコープ外の変更となり、レビュー負荷が増える
- NEVER add features or abstractions beyond what the plan specifies — スコープ外の変更は予期しないバグを引き起こす
- ALWAYS update the checklist after each implementation step — 中断時に再開位置がわからなくなることを防ぐ
- ALWAYS run type check and lint after each implementation step (if available) — 各ステップ後の検証で問題の原因特定が容易になる
- Run the full test suite only ONCE at the end (Phase I-3), not after every step — テスト実行コストを最小化するため
- If a step's target file doesn't exist for a "modify" action, flag it and ask the user — 存在しないファイルへの変更は意図しない結果を生む
- If the plan file changes during implementation, re-read it before each step — ユーザーの修正意図を反映するため
- Respect CLAUDE.md conventions if the file exists — プロジェクト規約に反するコードはlint/reviewで却下される
- Keep the implementation faithful to the plan — do not deviate or "improve" beyond what's specified — 計画からの逸脱は承認プロセスのバイパスとなる
- Correctly pass data between phases (RESEARCH_FILE, OUTPUT, etc.) and maintain variable consistency — フェーズ間のデータ不整合はサイレントに誤った結果を生む
